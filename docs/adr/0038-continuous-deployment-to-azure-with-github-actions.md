# 0038: Continuous deployment to the Azure VM with GitHub Actions, GHCR, OIDC, and run-command

- Status: accepted
- Date: 2026-10-04
- Amends: [ADR 0019](0019-single-host-compose-deployment.md) ("images are built on the VM; nothing is pushed to a registry") for the continuous deployment path; the build-on-the-VM path stays for local and manual use.
- Builds on: [ADR 0037](0037-cloud-secret-management-with-azure-key-vault.md) (the VM reads its secrets from Key Vault with its managed identity).

## Context

The demo runs on one Azure VM with `deploy/compose.prod.yml` behind Caddy (ADR 0019), its secrets staged from Key Vault (ADR 0037), and is operated by hand with `deploy/prod.sh` over SSH: pull the commit, build the images on the VM (about five minutes, and memory the 4 GB VM also needs for the stack), back up, migrate, start, then run the smoke test and the CSP check from a laptop. Every merge to `main` until the award ceremony (2026-10-16) needs that sequence, and a missed step (no backup, no CSP check, building a commit CI never passed) is the likely failure. The team wants merges to reach the VM automatically, without giving GitHub a long-lived Azure credential or the VM a standing GitHub credential, without opening SSH to GitHub's address ranges, and with a rollback that does not depend on someone being awake.

## Considered options

1. **Build on GitHub, push to GHCR, sign in to Azure with OIDC, release through `az vm run-command invoke`.** Images are built once per commit by the workflow that already has the source, tagged with the commit SHA, and pulled by digest on the VM. Azure trusts a federated credential bound to the repository's `production` environment, so no client secret exists; the identity's only right is run-command on the one VM. No inbound port changes. Run-command executes as root and reports success whatever the script's exit status, allows one command at a time, and returns only the last 4 KB of output; the scripts must handle all three.
2. **The same build, but deploy over SSH** from the runner. Exit codes and full output are native, but port 22 must accept GitHub's large and changing address ranges (or a self-hosted runner, or a bastion), and an SSH private key becomes a long-lived GitHub secret that opens a shell on the VM.
3. **Keep building on the VM**, triggered by the workflow (run-command or SSH calling `prod.sh update`). No registry, but every deploy costs the VM's CPU and memory during the build, the images are not the ones CI scanned, and the VM's checkout needs the build toolchain's network access.
4. **Azure Container Registry with the VM's managed identity (AcrPull) and OIDC for the push (AcrPush).** No GitHub token reaches the VM at all, but it adds a paid Azure resource and a second registry beside GHCR, for one VM and twelve days.
5. **A pull agent on the VM** (Watchtower or a timer polling GHCR). No inbound control path, but it needs a standing registry credential on the VM, deploys whatever tag moves, and has no place to run the smoke and CSP checks or to decide a rollback.

## Decision

Option 1, as `.github/workflows/deploy.yml` with scripts in `deploy/azure/`:

- **Trigger.** `workflow_run` on the `ci` workflow completing with success for a push to `main`, only for the commit that is still the head of `main` (CI runs can finish out of order), and only while the repository variable `DEPLOY_ENABLED` is `true`; plus `workflow_dispatch` from `main` with `deploy` or `rollback`. Until `AZURE_VM_NAME` and `PUBLIC_URL` exist the workflow stops at its plan job with a notice, so merging this changes nothing before the human's setup.
- **Build once.** The `build` job (permissions `contents: read`, `packages: write`) runs the commands of `make images`, labels the images with their source and revision, pushes `ghcr.io/<owner>/<repository>/bank-agent-{api,job,web}:<commit SHA>`, and records each digest. `VITE_DEMO_MODE` (baked into the SPA) comes from a repository variable.
- **Release.** The `deploy` job runs in the `production` environment (the human adds required reviewers and the main-only branch rule there) with `contents: read`, `id-token: write`, and `packages: read`. `azure/login` exchanges the job's OIDC token; `deploy/azure/run-on-vm.sh` validates every value and sends `deploy/azure/vm-deploy.sh` through run-command with the settings as `export` lines inside the script, never as arguments. On the VM, as the checkout's owner (never root): fetch and check out the commit, then `deploy/prod.sh release`: `pull` by digest and tag the images as `build` would (so `up`, `rollback`, and the state files are unchanged), back up the database when it runs, and `up`, whose `migrate` job must succeed before the API is replaced. A failed release starts the previous commit and tag again at once.
- **Registry access from the VM.** The deploy job's own `GITHUB_TOKEN`, with `packages: read`, revoked by GitHub when the job ends (minutes later). On the VM it goes only into a mode 600 file for `docker login --password-stdin` inside a throwaway Docker config, deleted afterwards. If the repository and its packages are public, the token is still passed but unnecessary.
- **Verify and roll back.** The same job runs `deploy/smoke_test.sh` and `make csp-check` against `PUBLIC_URL`. If either fails after a successful release, it signs in again and runs `run-on-vm.sh rollback` (`deploy/prod.sh rollback` with the previous release's commit checked out), so the rollback needs no second approval. The VM keeps the current and the previous images only.
- **Identity.** `deploy/azure/setup-github-oidc.sh` (run once by the human, idempotent, with a dry run) creates the app registration and service principal with no secret, the federated credential for `repo:<owner>/<repository>:environment:production` and, by default, one for `refs/heads/main`, and a custom role with exactly `Microsoft.Compute/virtualMachines/read` and `.../runCommand/action`, assigned on the VM (or Virtual Machine Contributor on the resource group with `ROLE_MODE=builtin`). It gets no Key Vault role: the VM's managed identity keeps that.
- **Hygiene.** `permissions: {}` at the top and the minimum per job, one deploy at a time (`concurrency`, never cancelled half-way), actions pinned by commit SHA, no secret echoed (the ids are environment secrets so jobs outside the environment never see them). `make security` and CI run actionlint (with shellcheck) on every workflow and shellcheck on the new scripts.

## Consequences

- A merge that passes CI reaches the VM in about fifteen minutes with a backup, a migration, the smoke test, and the CSP check every time, and a failed check rolls back without anyone watching. The judges see the same images CI built from the reviewed commit.
- **Run-command is root on the VM.** Whoever can obtain the identity can run anything there, including reading the staged secrets. The identity is reachable only from a workflow job in the `production` environment (and, while the branch credential exists, from a job on `main` that asks for `id-token: write`; no other workflow does, and `BRANCH_CREDENTIAL=0` removes that path). Required reviewers on the environment and branch protection on `main` are therefore part of the control, and the human sets both.
- **A short-lived GitHub token reaches the VM**, inside the run-command script that Azure delivers to the VM's agent (root-only on the VM). It can read the repository and its packages until the job ends.
- **Rollback swaps images, not data.** Migrations only move forward; when a release ran a migration the previous code cannot use, the automatic rollback starts old code on the new schema. The backup taken by `release` and `deploy/prod.sh restore` remain the way back, by hand (`deploy/README.md`).
- **The VM's checkout must be able to fetch the commit**: a public repository, or the read-only deploy key from the Key Vault guide configured as the checkout's `core.sshCommand`. The operator account needs passwordless sudo (for the secret stager) and the `docker` group, as Azure's admin user has.
- The smoke test and the CSP check sign in as demo personas, so the public demo must be seeded and in demo mode; they change no demo data. Each deploy uses GitHub Actions minutes and GHCR storage; the VM prunes old images, GHCR keeps every SHA until someone deletes the package versions.
- If the stack later moves to managed services (ADR 0019's migration path), the build and the OIDC sign-in stay and the run-command step is replaced by the platform's own deploy.
