# 0022: A committed, bounded, pseudonymized organizer sample, and an explicit data source

- Status: accepted
- Date: 2026-09-26

## Context

The full organizer dataset (5.3 GB) cannot go into git, and reading it needs credentials that evaluators and CI do not have. Without organizer rows in the repository, a fresh clone can build nothing real: tests would run only on team fixtures, and a reviewer browsing GitHub could not see what the data looks like. CLAUDE.md rule 5 allows exactly one bounded, documented extract. During the phase the human added two requirements: a small human-readable preview of every table, and one obvious command each way to build from the sample or from the full data, with the source explicit, recorded, and never mixed.

## Considered options

1. **Commit only team-made fixtures.** No organizer data risk, but the pipeline would never run on real values in CI or a fresh clone, and the fixtures would not show the real vocabularies (Spanish product types, orphans, templated transcripts) that the contracts must handle.
2. **Commit the full data or whole tables.** Everything reproducible offline, but 5.3 GB in git, direct identifiers in the open, and a likely conflict with the organizer's data-use terms.
3. **Commit a hand-picked extract.** Small, but not reproducible, open to selection bias, and easy to get wrong on identifiers.
4. **Commit a deterministic, bounded, pseudonymized extract generated by the pipeline**, with a provenance README and a guard in `make check`.

## Decision

Option 4, as `make data-sample` (`bank-data sample`):

- **Selection.** Customers ranked by `sha256(seed || ':' || customer_id)`; the first 70 are taken, then only customers that cover a missing workflow case (cards, deposit balances, payments and transfers in all four statuses, credit products with and without days past due, income present and missing, a declined card purchase, at least five complaints). Each customer is followed through every table, fact rows limited to the last 365 days and capped per customer; branches, agents, campaigns, and exchange rates only when referenced. Result: 74 customers, 2,470 rows.
- **Bounds.** At most 5,000 rows in total (preview included; 2,595 today), never a whole table (checked against the delivery's counts), and `scripts/checks/check_data_sample.py` in `make check` and CI recounts every file against the README.
- **Pseudonymization.** Document numbers, names, emails, phones, addresses, and birth dates (customers and agents), plus product numbers and IP addresses, are replaced by values derived from `sha256(table, column, row key)` with no secret, format-valid for the contracts, and never equal to any original value of the column in the sample. Free text was profiled and holds no identifiers.
- **Format.** Raw CSVs in the bucket layout, so `LocalSource` ingests the sample exactly like S3 and every contract applies. The output is byte-identical for the same dataset version and seed, so the README carries no timestamp.
- **Preview.** `preview/<table>.csv` holds the first ten rows of each table with the same pseudonyms, and the README shows each table's columns with three example rows. `LocalSource` ignores `preview/`.
- **Explicit source.** `BANK_DATA_SOURCE` (`sample` by default, or `s3`) or `make ... DATA_SOURCE=` selects the source. Each source has its own warehouse directory (`data/warehouse-sample`, `data/warehouse`), the manifest refuses a second source, and the source appears in every command's output, the quality report, and the lineage page. Reports from a non-organizer source never overwrite the committed docs. `make pipeline` builds from the sample offline; `make data-download` then `make pipeline DATA_SOURCE=s3` builds from the full delivery.

## Consequences

- A fresh clone builds bronze, silver, and gold from real (pseudonymized) organizer rows in about 30 seconds, and CI can too.
- The sample reflects the data's quirks, which keeps the contracts honest, but it is not statistically representative: the coverage walk over-represents rare statuses. Final numbers always come from the full delivery.
- Regenerating needs the S3 warehouse; a new delivery or seed changes the files, and the README records the dataset version (etags and digests) so the change is traceable.
- The organizer's data-use terms must be checked before the repository becomes public (phase 17). If they forbid redistribution, the team asks the human before publishing and never rewrites history without explicit instruction.
- About 800 small files enter git (one per daily partition that a sampled row touches); acceptable for a bounded sample, and the layout fidelity is worth it.
